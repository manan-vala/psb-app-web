# Sentinel — Two-App Analysis
*Behavioural-biometrics fraud-detection demo · CBI Hack 2026*

This report documents a full crawl and interactive walkthrough of two linked Vercel deployments that make up one hackathon project: a customer-facing "capture layer" and an internal analyst dashboard. Both were explored screen-by-screen using Firecrawl (map, scrape, and a live interactive browser session) since neither app exposes a crawlable sitemap — content only appears after JavaScript renders and, for App 1, after buttons are clicked.

## 1. What this project is

Both sites share one visual identity ("Sentinel", navy/dark theme, Inter + IBM Plex Mono fonts) and appear to call the same backend API, `https://barelymadeit-9-cbihack2026.onrender.com`. Together they simulate a bank's behavioural-biometrics fraud system:

- **App 1** (root domain) is the consumer simulator — a fake UPI app and fake NetBanking portal that capture keystroke, touch, motion, navigation, and device telemetry while a customer "banks," then score the session for risk.
- **App 2** (the "-dnys" subdomain) is the analyst / fraud-ops console — dashboards, queues, and behavioural-analytics views that a bank's risk team would use to monitor sessions generated by App 1.

The project name in the URL ("barely-made-it-9-cbi-hack2026"), the placeholder/zero-value dashboards, a stubbed "AI Copilot" marked *In development*, and pre-seeded dummy data all indicate a hackathon MVP rather than a production system.

## 2. App 1 — barely-made-it-9-cbi-hack2026.vercel.app

Title: "Sentinel — Behavioral Capture Layer". Built with Vite + React and served as a single URL — there is no client-side router; every "screen" below is a state change on the same page (confirmed: the URL never changes when navigating). This is why an automated sitemap crawl (`firecrawl_map`) returns zero links — the app has to be driven interactively.

### 2.1 Landing screen

Hero copy: *"We capture how you bank — not just what you do."* Sub-copy explains that every keystroke, touch, tilt and hesitation is captured live and assembled into a behavioural signal vector for a fraud-risk model.

- Customer identity selector — a dropdown to act as "Guest (no profile)" or as one of 100 pre-seeded dummy users (dummy_0001–dummy_0992, e.g. "Dummy User 346").
- Two top-level actions: **Register →** and **Customers (100) →**.
- Two entry cards: 📱 **UPI Payment** ("Mobile-first" — touch · motion · keystroke · transaction) and 💻 **Internet Banking** ("Best on this device" — keystroke · navigation · transaction).
- Footer shows live device fingerprinting, e.g. "Detected: desktop · 1920x1080 @1x · secure context ✓ · fingerprint #cb2dd378".

### 2.2 UPI Payment flow ("Sentinel Pay")

A mobile-styled payment splash screen ("Unified Payments · Secure by behaviour", *Tap to begin*) paired with a live telemetry sidebar that updates in real time. The sidebar tracks **63 total signals across 10 families**:

| Signal family | Feature count |
|---|---|
| Keystroke | 9 |
| Touch | 8 |
| Motion | 9 |
| Navigation | 7 |
| Transaction | 4 |
| Session | 4 |
| Location | 5 |
| Network / IP | 5 |
| Device | 8 |

The sidebar also live-streams: keystroke dwell/flight times, device motion (pitch/roll/yaw), touch pressure & tap area, IP geolocation and ISP/ASN, GPS status, and a full device fingerprint (platform, secure context, CPU cores, memory, screen size, canvas hash). A "Live capture · JSON" panel shows the exact model-ready payload being assembled (fields such as `pin_events`, `touch_events`, `motion_events`, `navigation_events`, `transaction_context`, `geo_network_events`, `security_events`). Fields explicitly not web-capturable (cell tower ID, IMEI, SIM serial, carrier, Wi-Fi BSSID) are shown as placeholders, labelled "native-SDK only."

### 2.3 Internet Banking flow ("Sentinel NetBanking")

A realistic desktop netbanking login page ("eBWServer5", "🔒 Secured session") with Customer ID / User ID and Password fields, a virtual on-screen keyboard toggle, and a note that pasting the password is flagged as anomalous (demo credential: `demo1234`). The same live-capture sidebar as the UPI flow runs alongside it, oriented toward keystroke dynamics rather than touch/motion.

### 2.4 Session Report ("Sentinel AI · Identity & Fraud Intelligence")

Reached via **"End & view report →"**. This is the most detailed screen in the app — a full explainable-AI risk verdict for the session just captured:

- Headline scores: Trust Score (e.g. 23/100), Risk Score (e.g. 77/100 → "High Risk / Step-Up Authentication Triggered"), Behaviour Anomaly Score (0–100), session metadata (channel, session ID, timestamp, model name).
- Identity Assurance panel: Face ID (performed/skipped), Behaviour (server-scored), Device confidence %, Location confidence %.
- AI Decision Rationale: plain-language reasons verification was triggered, plus weighted Trust Signals (e.g. "Familiar login location +12") and Risk Signals (e.g. "No keystroke telemetry captured −33", "Device/IP timezone mismatch −18").
- Personalised Baseline Deviations table — per-feature baseline mean (μ), current-session value, Z-score, and a 0–100 contribution weight, scored with a model the UI names **hybrid-v2-mahalanobis**, using Welford's algorithm for online baseline stats and requiring 3 sessions before it's "confident."
- Authentication Timeline, Cross-Session Comparison (against prior sessions of that identity), and a Behavioural Biometrics breakdown (keystroke timing, pressure sensitivity, 3-axis device motion) with a "human vs bot/remote-access" framing.
- Network & Location Context (IP, ISP/ASN, GPS↔IP gap, device fingerprint) and Forensic Session Data — the complete raw JSON telemetry payload, copyable and downloadable as `.json`.

## 4. How the two apps relate

App 1 is the data-generation surface: every simulated UPI/NetBanking session run there posts its 63-feature telemetry payload and risk verdict to the shared backend. App 2 is the consumption surface: it reads that same backend to power fleet-wide analytics (Executive, Product Intelligence), per-customer drill-down (Customer 360), and operational triage (Fraud Operations). The 52,800+ sessions and 100 customers visible in App 2's dashboards line up with App 1's dummy-user roster and its session-generation flows, strongly suggesting the two apps are two frontends over one backend/dataset (`https://barelymadeit-9-cbihack2026.onrender.com`), built for a hackathon ("CBI Hack 2026") to demonstrate an end-to-end behavioural-biometric fraud-detection product: **capture → score → operate**.

## 5. Technical notes

- Both apps are Vite-built React SPAs deployed on Vercel, sharing a design language (dark navy theme, Inter / IBM Plex Mono fonts, an "S" logomark).
- App 1 has no client-side router — all screens are React state changes on a single URL, so it must be crawled interactively (this report used a live Firecrawl browser session) rather than via sitemap/link discovery.
- App 2 uses react-router with 7 static paths, discoverable both via its compiled JS chunk map and by requesting each path directly (each returns a full SPA shell with correct content — a working SPA fallback rather than 404s).
- Both apps' KPI values (52.8K sessions, 1.0K customers, ~93/100 avg trust, 0 high-risk/blocked) look like seeded/simulated demo data rather than live production traffic — consistent with a hackathon proof-of-concept.
